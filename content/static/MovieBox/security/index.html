安全说明

最后更新：2026 年 10 月 19 日

本页说明「保险箱」等功能的技术实现与能力边界。 关于我们收集什么数据，请看 隐私政策。

一、保险箱加密是怎么做的

  • 算法：AES-256-GCM（带认证的加密，密文被篡改会被发现）
  • 方式：原地加密 —— 只把文件前 1 MB替换为密文，其余部分保持原样，文件大小不变
  • 元数据：原始文件名、IV、认证标签、原始文件头明文备份保存在同目录的 -meta 侧车文件中
  • 密码派生：密钥由密码推导，只存在于内存中，退出应用即清除

二、它的能力边界（请务必了解）

保险箱的设计目标是「让其他程序认不出、打不开这个文件」，不是抵御专业取证。具体来说：

  • 它不是全盘加密，也不加密文件尾部 —— 1 MB 之后的内容仍是明文
  • 它能挡住「双击打不开、播放器不识别、预览看不到」这类日常场景
  • 它不能抵挡掌握你电脑和加密知识的人故意提取
  • 如果你需要真正的机密保护，请使用 VeraCrypt、FileVault 等全盘/容器加密方案

三、密码丢失

密码无法找回，也没有后门。MovieBox 不保存你的密码，开发者也无法帮你恢复。 请自行妥善保管。忘记密码意味着加密文件无法还原。

四、崩溃与异常保护

  • 加密顺序为「先写 meta 备份 → 再覆盖文件头 → 最后改名」，写入前后都有 fsync 落盘
  • 解密可重入：中途断电强杀后再次解密，能识别「头部已是明文」的状态并安全收尾，不会二次破坏
  • 删除 meta 前会先备份为 -meta.bak，完整还原成功后才删除备份
  • 同一文件的加解密操作串行执行，避免并发写坏文件头

即便如此，重要文件请先备份再加解密。

五、网络磁盘

  • 网络磁盘（SMB / NFS / AFP）上的文件不做加解密，也不显示加密入口
  • 凭据用系统方式传递（macOS 走 Finder 挂载，Windows 用 net use 参数数组）， 不以明文拼进命令行
  • 磁盘断连时不会删除你的库记录；读取失败的目录整棵子树会被保留

六、更新通道

更新包通过 GitHub Releases 分发，macOS 版本使用 Developer ID 证书签名。

七、报告安全问题

发现安全相关的问题，请在 GitHub Issues 提出。 如涉及敏感细节，可先只描述现象，我们再私下沟通细节。
